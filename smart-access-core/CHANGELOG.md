# 1.1.10

- **Главная причина «нет связи» с Frigate 0.16+ найдена и исправлена**:
  `/api/version` у Frigate отвечает **plain text'ом** (PlainTextResponse,
  например `0.18.2` — док.: docs.frigate.video/integrations/api), а Smart
  Access требовал JSON. Живой Frigate выглядел как «HTTP 200, но тело не JSON
  (text/plain)» → «нет связи», хотя API работал (в журнале Frigate при этом
  видно `frigate.api.auth: Anonymous user access …`). Теперь тело
  `/api/version` разбирается и как plain text, и как JSON-строка, и как
  `{"version": …}`; якорь версии на начало строки исключает ложные
  срабатывания на HTML.
- Порты приведены к официальной документации
  (docs.frigate.video/configuration/advanced/system, «Listen on different
  ports»): **5000 — внутренний, БЕЗ аутентификации (права администратора) —
  приоритетный порт интеграции; 8971 — внешний, ТРЕБУЕТ аутентификации (и TLS
  у 0.16+)**. Порядок авто-поиска теперь (5000, 8971).
- HTTP 400 от 8971 больше не вводит в заблуждение: при выключенной
  аутентификации внешний порт отвечает 400 — это ожидаемо, подсказка прямо
  говорит «используйте внутренний 5000»; ответ 400 так же уводит проверку на
  https (TLS-порт может отвечать 400 на plain-HTTP запрос любой формулировкой,
  не только «HTTPS server»).
- Новый статус `HTTP 401/403` — «Frigate найден, но порт требует
  аутентификацию»: отдельный вид ошибки и подсказка (порт 5000 без
  аутентификации либо `auth: enabled: false`).
- Диагностика через Supervisor API дополнена hostname аддона Frigate: в
  подсказке появляется готовый внутренний адрес
  `http://<имя-аддона>:5000` (например `http://ccab4aaf-frigate-fa:5000`).
- **Хвост журнала аддона Frigate прямо в панели** (Supervisor API,
  `/addons/<slug>/logs`): если связи нет, в карточке «Состояние» раскрывается
  «Журнал аддона Frigate (последние строки)» — причина (ошибка в config.yml и
  т.п.) видна сразу, копировать логи вручную не нужно. Кэш 60 с, запрашивается
  только при отсутствии связи.
- Подсказки переписаны под официальную документацию; DOCS.md дополнен
  разделом о семантике портов и формате `/api/version`.

# 1.1.9

- Самодиагностика связи с Frigate, когда не помогают ни настроенный адрес,
  ни внешние порты хоста (как в реальном кейсе «refused» и на 8971, и на 5000):
  * поиск Frigate по **внутренней сети аддонов** (docker-мост hassio,
    стандартно 172.30.32.0/23; из host-network аддона контейнерные IP доступны
    напрямую — публикация портов вообще не нужна). Найденный адрес
    `http://<IP-контейнера>:5000` показывается в панели и сразу используется,
    включая снапшоты распознавания; при смене IP после перезапуска Frigate
    адрес ищется заново (троттлинг скана 60 с, кэш 10 мин). Подсети можно
    задать вручную: env `SMART_ACCESS_BRIDGE_SUBNETS`.
  * диагностика через **Supervisor API**: если связь так и не найдена,
    аддон сообщает, установлен ли аддон Frigate вообще, запущен ли он
    («Запустите: Настройки → Аддоны → Frigate → Запустить») или запущен, но
    недоступен («смотрите Журнал аддона — вероятно, падает при старте»);
    если Frigate не аддон, а отдельный сервер — подсказка указать
    `http://<IP-сервера>:5000`.
  * TLS: Frigate 0.16+ по умолчанию включает HTTPS (self-signed) на 8971 —
    проверка связи теперь пробует `https` c `verify=False`, если по `http`
    получена SSL-ошибка.
- Supervisor API: база `http://supervisor` из host-network аддона может не
  резолвиться — добавлен фолбэк на IP-алиас Supervisor `172.30.32.2`
  (кэш 10 мин, автоопределение при первом запросе). Это же страховка для
  вызовов HA-сервисов и снапшотов камер.
- MQTT: если в опциях брокер указан как `localhost`/`127.0.0.1`/пусто — адрес
  автоматически становится `127.0.0.1`, а логин/пароль берутся у Supervisor
  (сервис mqtt:want). Раньше `mqtt.host=localhost` блокировал обнаружение
  кредов, и подключение шло без аутентификации — события Frigate не доходили.
  В панели рядом с хостом брокера показывается статус подключения
  («подключено» / причина).

# 1.1.8

- Авто-поиск порта Frigate. У аддона Frigate «Внутренний порт» (5000) и
  «Внешний порт» (8971) — не одно и то же: наружу, на хост, публикуется
  только внешний, поэтому дефолтная связка по `http://127.0.0.1:5000` из
  соседнего аддона давала «Connection refused», хотя Frigate работал. Если
  настроенный `frigate_url` не отвечает, Smart Access теперь сам проверяет
  типовые порты того же хоста (8971, 5000): найденный адрес показывается в
  панели («Frigate найден автоматически на … , впишите его в Frigate URL»)
  и сразу используется системой — статус и загрузка снапшотов для
  распознавания не ломаются, пока в настройках остался неверный порт.
- Ответ `/api/version` проверяется на JSON: HTML-страница (включённая
  аутентификация Frigate, WebRTC-порт 8556, чужая служба) больше не
  считается успешной связью; подсказка различает «порт не тот» и «на
  8971 живёт Frigate, но с включённой аутентификацией».
- Подсказка при «Connection refused» переписана под обе панели настроек
  Frigate: «Внешний порт» (по умолчанию 8971) и «Unauthenticated Web
  interface» (впишите 5000) в оригинальном аддоне; объяснено, почему
  «Внутренний порт» с хоста недостижим.
- Панель: рядом с «связь есть» показывается версия Frigate.
- Дефолт `frigate_url` для новых установок: `http://127.0.0.1:8971`.

# 1.1.7

- Критическое исправление панели под ingress. Панель открывается по адресу
  `/api/hassio_ingress/<токен>/`, но все запросы в JS были с корневым путём
  (`fetch('/api/...')`) — браузер отправлял их в **корень Home Assistant**,
  а не в аддон: HA отвечал HTML-страницей, и панель показывала «ошибка
  загрузки статуса: Unexpected token '<'…», а генератор выдавал HTML вместо
  конфига. Все запросы переведены на базу относительно документа
  (`API('api/...')`) — работает и под ingress, и при прямом открытии
  `http://<IP>:8099`. Это же было причиной «ошибки загрузки
  статуса» в предыдущих версиях.
- Проверено сквозным тестом через прокси с отрезанием ingress-префикса:
  страница, status, frigate-config, events, subjects возвращаются корректно.

# 1.1.6

- Диагностика Frigate в панели вместо молчаливого «нет связи»: `/api/status`
  теперь возвращает `frigate_error` — понятную причину (неверный порт,
  соединение отклонено, HTML вместо API) и что делать. Подсказка различает
  главные ошибки: порт 8556 у аддона Frigate — это WebRTC (go2rtc), HTTP API
  живёт на порту 5000; для доступа из соседнего аддона порт 5000 надо
  опубликовать (Frigate → Конфигурация → Сеть → «Unauthenticated Web
  interface» → 5000).
- Проверка Frigate больше не блокирует event loop синхронным requests
  (запрос в executor + кэш 10 с) — панель перестаёт «подвисать», если адрес
  Frigate недоступен/медленный.
- Генератор конфига Frigate исправлен под сетевую модель аддонов:
  * `mqtt.host` из опций (localhost/127.0.0.1/пусто) заменяется на
    `core-mosquitto` — аддон Frigate работает в мостовой сети hassio и не видит
    localhost, брокер для него — соседний аддон по имени;
  * мост камер подставляется как `http://172.30.32.1:8100/mjpeg/<name>`
    (шлюз hassio-сети = хост, где слушает Smart Access с host_network), а не
    `127.0.0.1:8100`, который у Frigate указывал на его собственный контейнер.
- UI: текст причины ошибки Frigate показывается в карточке «Состояние»
  (с экранированием), сообщение об ошибке загрузки статуса теперь содержит
  саму ошибку fetch — проще диагностировать ingress-сбои.

# 1.1.5

- Исправление: приложение пропадало из Магазина аддонов после 1.1.4. В свежих
  версиях Supervisor `watchdog` в config.json — это не булево значение, а
  строка-URL (как `webui`); `"watchdog": true` не проходит валидацию, и
  Supervisor молча отбраковывает приложение при сканировании репозитория.
  Установлено `"watchdog": "http://[HOST]:[PORT:8099]"` — Supervisor пингует
  web-интерфейс и перезапускает контейнер, если тот не отвечает.
- Схема config.json сверена с исходниками Supervisor (apps/validate.py):
  все остальные ключи валидны, `init: false` — корректное булево поле.

# 1.1.4

- Исправление crash loop `s6-overlay-suexec: fatal: can only run as pid 1`:
  Supervisor по умолчанию запускает контейнер аддона с docker `--init` (tini
  становится PID 1), а s6-overlay из базового образа HA обязан быть PID 1 —
  контейнер умирал мгновенно, до Python дело не доходило. Добавлены
  `"init": false` (s6 становится PID 1) и `"watchdog": true` (авто-рестарт
  при падении).
- run.sh подключён как главная служба: `COPY run.sh /run.sh` +
  `CMD ["/run.sh"]` — s6-overlay v3 запускает CMD автоматически.

# 1.1.3

- Исправление падения при старте (crash loop): код копировался в образ плоско
  (`COPY app /app`), а `main.py` импортирует `from app import ...` — пакет `app`
  в контейнере не находился, процесс завершался с `ModuleNotFoundError` сразу
  после запуска. Теперь код кладётся пакетом `/app/app`, задан `PYTHONPATH=/app`,
  путь в `sys.path` вычисляется от расположения файла (устойчиво к обеим
  компоновкам).
- В образ добавлены системные библиотеки `libstdc++6` и `zlib1g`, которые нужны
  opencv/onnxruntime и отсутствуют в минимальном базовом образе HA.

# 1.1.2

- Установка стала быстрой и с прогрессом: Supervisor больше не собирает образ
  на устройстве, а скачивает готовый из GHCR (`ghcr.io/noidxmv6/smart-access-core-{arch}`,
  собирает GitHub Actions). Из образа убран ffmpeg (кодом не использовался) —
  объём скачивания заметно меньше.
- Модели (CLIP/SFace/YuNet, ~128 МБ) больше не хранятся в git-репозитории —
  раздаются через GitHub Release `models-v1`, в образ вшивает CI; при их
  отсутствии run.sh скачает их при первом запуске. Добавление репозитория
  в Магазин аддонов теперь занимает секунды вместо минут.
