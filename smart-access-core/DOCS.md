# DOCS.md — Smart Access Core (справка аддона)

Краткая справка отображается в карточке аддона.

## Установка и настройка (кратко)

Полное пошаговое руководство — в [README репозитория](https://github.com/NoIDXMV6/ha-smart-access#установка-по-шагам). Ключевые моменты:

1. **Mosquitto broker** установлен и запущен. Пользователя MQTT для Frigate
   создайте через Настройки → Люди → Пользователи (проще всего) или в аддоне
   Mosquitto, секция Logins. Имя не может быть `homeassistant`/`addons`.
2. **Frigate** ставится из репозитория аддонов
   `https://github.com/blakeblackshear/frigate-hass-addons`
   (главный репозиторий `blakeblackshear/frigate` магазин не примет —
   там нет аддонов).
3. **Конфиг Frigate** вводится не на странице «Конфигурация» аддона, а в
   веб-интерфейсе Frigate (редактор конфигурации) или в файле
   `/addon_configs/ccab4aaf_frigate/config.yml`. Проще всего сгенерировать
   кнопкой «Сгенерировать» в панели Smart Access и вставить.
4. Этот аддон: заполните поля в UI (камеры, исполнители, пороги, VLM) —
   без правки файлов — и нажмите «Запустить». Установка — скачивание готового
   образа ~0,5 ГБ с прогрессом в карточке аддона (1–5 минут), ничего на
   устройстве не собирается.
5. MQTT-поля в настройках аддона можно оставить пустыми: учётные данные
   брокера берутся у Supervisor автоматически.
6. **Интеграция Smart Access (HACS) — обязательный второй компонент**, из того же
   репозитория: она создаёт сенсоры `sensor.smart_access_*`, сервисы
   `smart_access.enroll/identify` и кнопку «Обучить» на карточках. Аддон без
   неё не управляет HA, интеграция без аддона не получает данные.

## Что делает

* Раздаёт камеры HA (включая облачные А.М.Видео/ЕГДС) локальным MJPEG-потоком
  для Frigate: из сети аддона Frigate поток доступен как
  `http://172.30.32.1:8100/mjpeg/<name>` (шлюз hassio-сети = хост, где слушает
  этот аддон; генератор конфига подставляет его сам). До 1.1.11 порт 8100
  фактически не слушался (в логе аддона сообщение о нём было ложным) — отсюда
  «Connection to tcp://172.30.32.1:8100 refused» в журнале Frigate.
* Камеры с заполненным полем `rtsp_url` идут во Frigate напрямую (TCP-транспорт
  подставляется генератором), мост для них не тратит ресурсы.
* Слушает события Frigate (MQTT), распознаёт машины (CLIP, CPU) и лица (SFace).
* Открывает исполнителей через HA: `executor_service` + `executor_target`
  (например `amvideo.open_barrier` + `button.1_shlagbaum_..._otkryt`,
  `lock.unlock` + `lock.gate`).
* Ведёт базу «своих»: фото в `/media/smart_access/{cars,faces}/<имя>/`,
  эмбеддинги в `/data/db/`.

## Камеры: список, имена, пример на три камеры

Камеры задаются списком `cameras` в настройках аддона (не в файлах). Имя каждой
камеры — это и имя камеры во Frigate, и имя MJPEG-потока моста
(`/mjpeg/<имя>`), поэтому оно должно соответствовать формату Frigate —
только `a-z 0-9 _`. Кириллицу и точки писать не нужно: 1.1.11+ сама
нормализует имена (транслит) и предупредит в журнале, например
«а.м.видео» → `a_m_video`, «егдс» → `egds`, «калитка» → `kalitka`.

Пример конфигурации на три камеры (подставьте свои `ha_entity`):

```json
"cameras": [
  { "name": "am_video", "ha_entity": "camera.1_shlagbaum_derevnia_govorovo_15072_kamera",
    "mode": "car", "executor_service": "amvideo.open_barrier", "cooldown": 45, "enabled": true },
  { "name": "egds", "ha_entity": "camera.egds_..._vhod",
    "mode": "car+face", "executor_service": "", "enabled": true },
  { "name": "kalitka", "ha_entity": "camera.kalitka_...",
    "mode": "face", "executor_service": "lock.unlock", "executor_target": "lock.gate",
    "cooldown": 30, "enabled": true }
]
```

После сохранения настроек панель и генератор конфига Frigate сразу покажут все
камеры (в таблице — `fps` моста: если у камеры с подключённым Frigate `fps: 0`,
значит Frigate не читает поток — проверьте, что конфиг Frigate содержит
`http://172.30.32.1:8100/mjpeg/<имя>` и что камера живая в HA). С 1.1.13 мост
опрашивает камеры ПАРАЛЛЕЛЬНО: реальный fps каждой камеры не зависит от числа
камер и медленных облачных снимков соседей.

## «No frames received from <camera> in 20 seconds» — цикл перезапуска ffmpeg

Симптом: у МОСТОВОЙ камеры (путь `http://172.30.32.1:8100/mjpeg/...`) во Frigate
«Поток офлайн», в журнале каждые 20 секунд
`watchdog.<камера>: No frames received ... in 20 seconds. Exiting ffmpeg...`,
а перед этим — строки `[swscaler] deprecated pixel format` и
`[in#0/mjpeg] Error during demuxing: Immediate exit requested`. При этом
плитки в HA показывают камеру нормально, `/mjpeg/<имя>` в браузере открывается,
а по сети байты идут (проверка `curl` это подтверждает).

Классическая причина — строка `input_args: -f mjpeg` во входе камеры (её писал
генератор до v1.1.13, шаблон в старом README). `-f mjpeg` заставляет ffmpeg
парсить поток СЫРЫМ демуксером mjpeg вместо multipart (mpjpeg): сырой демуксер
считает поток 25 fps и перед первым кадром набирает ~5 секунд «виртуального»
времени (~125 кадров). Мост отдаёт ~1.5 кадра/с, поэтому проба формата занимает
минуты — а watchdog Frigate убивает ffmpeg уже через 20 секунд. Цикл
повторяется бесконечно (воспроизведено на стенде: с `-f mjpeg` — 0 кадров за
20 с, без него — вход открывается мгновенно).

Лечение: панель Smart Access → «Конфиг Frigate» → «Сгенерировать» (в 1.1.13+
генератор пишет правильные аргументы) и вставить конфиг целиком, либо руками
заменить у мостовых камер строку `input_args: -f mjpeg` на:

```yaml
          input_args: >-
            -use_wallclock_as_timestamps 1
            -fflags +genpts+discardcorrupt
```

и перезапустить Frigate. `fps: 5` у мостовой камеры тоже поправьте на 2 —
мост отдаёт ~1.5 кадра/с (поле `bridge_fps`), детектору незачем ждать больше.

Если цикл остался, проверьте ещё две вещи:

* имя камеры в конфиге Frigate совпадает с `name` камеры в Smart Access:
  при несовпадении мост отвечает 404 с телом `{"error": "unknown camera"}`
  (ровно 27 байт — легко заметить в curl), а в журнале аддона появляется
  «запрос НЕИЗВЕСТНОЙ камеры»;
* у камеры в панели живой `fps > 0` при подключённом Frigate (с 1.1.13 в
  журнале аддона видно каждое подключение/отключение клиента моста).

## «Сбоев» растёт, fps: 0, во Frigate серая картинка — мост не получает кадры от HA

Симптом (реальный случай, камера `kalitka`): в панели у мостовой камеры
`сбоев: 440, fps: 0`; поток `/mjpeg/<имя>` отдаёт байты, но ровно ~5.4 КБ на
кадр (32388 байт за 4 с при 1.5 fps), а `latest.webp` во Frigate весит ~1 КБ —
это СЕРАЯ ЗАГЛУШКА «camera offline», а не камера. Frigate такую картинку
декодирует, но движения в ней нет — объектов и событий не появляется
(«в карточке калитка не найден объект»). Карточка в HA при этом играет,
потому что она читает ПОТОК камеры, а не одиночные снимки.

Причина: `camera_proxy` (одиночный снимок) для этой сущности в HA не работает.
Типичный носитель — универсальная камера (Generic Camera) с RTSP-потоком и без
«URL кадра» (still_image_url): ради ОДНОГО кадра HA запускает извлечение кадра
из потока (ffmpeg + HLS), это медленно и не укладывается в таймаут моста, зато
непрерывный MJPEG/поток у неё живой. До 1.2.1 причины писались на DEBUG, и
журнал аддона молчал — счётчик «сбоев» рос без объяснений.

Что делает 1.2.1:

* **Запасной путь**: если одиночный снимок не удался, мост берёт ОДИН кадр из
  потока HA (`/core/api/camera_proxy_stream/<сущность>`) — тот же путь, по
  которому играет карточка. Камера оживает и во Frigate (в панели у такой
  камеры плашка «кадр из потока HA»), но путь медленный (единицы кадров в
  минуту) — это режим деградации, а не полноценное решение;
* **Диагностика**: причины отказов пишутся в журнал аддона (WARNING,
  не чаще раза в минуту), в панели видны источник кадра, последняя ошибка и
  подсказка «что делать»;
* **Бэкофф**: при стойком сбое опрос повторяется через 1.3→2.7→5 с, а не
  каждые 0.67 с, и опросы одной камеры не наслаиваются — HA больше не
  нагружается десятками параллельных извлечений кадра, а соседние камеры
  моста не тормозят о застрявшую.

Полноценные решения (в порядке предпочтения):

1. **Локальная RTSP-камера → вписать `rtsp_url`** в настройках этой камеры
   Smart Access (например Hikvision:
   `rtsp://admin:пароль@192.168.168.77:554/h264/ch01/main/av_stream`).
   Frigate будет читать её НАПРЯМО (`preset-rtsp-tcp`, fps 5), мост для неё
   отключается — это путь камеры `tatyanin_park`. После сохранения сгенерируйте
   конфиг Frigate в панели и замените блок этой камеры.
2. **Универсальной камере в HA добавить «URL кадра»** (still_image_url),
   например у Hikvision: `http://admin:пароль@IP/ISAPI/Streaming/channels/101/picture`
   (спецсимволы пароля кодируются: `@→%40`, `:→%3A`, `/→%2F`). Тогда
   одиночные снимки станут мгновенными и мост заработает на полных 1.5 fps.

## «MQTT Not authorized» в журнале Frigate

Frigate подключается к брокеру со своими настройками — если user/password не
совпадают с брокером, в его журнале цикл «MQTT Not authorized / disconnected»,
а события `frigate/events` не доходят. Лечение: откройте панель Smart Access →
«Конфиг Frigate (генератор)» → «Сгенерировать» — блок `mqtt:` теперь содержит
РАБОЧИЕ креды (те же, под которыми подключается сам Smart Access: с 1.1.11
пароль подставляется автоматически из Supervisor, раньше вместо него была
заглушка «ВАШ_ПАРОЛЬ_БРОКЕРА»). Замените блок `mqtt:` в конфиге Frigate этим
блоком целиком и перезапустите Frigate. Конфиг с кредами не публикуйте.


## Обучение

* Кнопка «Обучить» на карточке → сервис `smart_access.enroll`.
* Панель Smart Access (вкладки «Машины» и «Лица»): добавление subject'а
  МНОЖЕСТВОМ фото сразу, галерея фото с миниатюрами, удаление ошибочных
  фото (отметить → «Удалить выбранные» — после удаления автоматически
  запускается переобучение), кнопка «Переобучить» у каждого субъекта.
* Сервис `smart_access.retrain` (kind: car|face, subject: опционально) —
  пересборка прототипов по фактическим фото `/media/smart_access/...`.
  Выполняйте после удаления фото и при обновлении моделей.
* Если карточка пишет «Действие smart_access.enroll не найдено»: обновите
  интеграцию (HACS) до 1.2.0+ и перезапустите Home Assistant. С 1.2.0
  сервисы регистрируются сразу при старте — даже без завершённой настройки
  интеграции.

## Жесты (подтверждение и тревога) — v1.2.0

Включаются тумблером во вкладке «Жесты и тревога» панели (или опцией
`gestures.enabled`). Требуют модель `/models/yolov8n-pose.onnx` — она вшита
в образ (статус модели видно в той же вкладке; без модели остальное работает).

* **Подтверждение — ОДНА рука вверх.** Лицо распознано как «своё» → открытие
  происходит только когда в кадре видна поднятая рука. Пока жеста нет —
  событие `gesture_wait` в журнале, открытия нет.
* **Тревога — ОБЕ руки вверх** (классический SOS): калитка открывается И
  одновременно отправляется инцидент:
  * MQTT `smart_access/event` с `action: "alarm"`;
  * постоянное уведомление в HA (кто, где, score);
  * звонки по тревожным номерам (если включены).

Правила считаются по ключевым точкам YOLOv8n-pose (точки 9/10 — запястья,
5/6 — плечи, COCO): запястье выше одноимённого плеча = рука поднята.

## Тревожные номера (SIP-звонок через ha-sip + TTS Piper)

Настройки аддона → блок `alarm`:

* `enabled` — включить звонки (дублируется тумблером в панели);
* `addon` — слаг SIP-аддона, по умолчанию `c7744bff_ha-sip`;
* `numbers` — по одному номеру в строке, например
  `sip:89256758881@pbx.kozhevatov.ru`;
* `sip_account` (1–3), `ring_timeout` (сек);
* `language` — язык озвучки TTS (например `ru`);
* `message_template` — текст звонка, плейсхолдеры `{name}` `{camera}`
  `{time}` `{date}`, по умолчанию «Тревога! {time}, {name} открыл калитку
  с тревожным жестом.».

Механика: `hassio.addon_stdin` → `command: dial`, `menu.message` = текст —
ha-sip озвучивает его настроенным в HA TTS-движком (Piper), `post_action:
hangup` кладёт трубку после сообщения. В ha-sip должен быть настроен
TTS-движок (`tts: engine_id`, debug_print: true подскажет доступные) и
`cache_dir`. Кнопка «Тест звонка» во вкладке «Жесты и тревога» звонит на
все номера с сообщением «Тест тревоги».

## Журнал: фильтры, архивирование

Вкладка «Журнал» панели: фильтры по типу (car/face), событию (opened/detected/
alarm/gesture_wait/unknown/denied/enrolled/retrained), камере, subject,
score (мин/макс) и дате (от/до). Хвост журнала — 2000 событий.

* «Архивировать текущий журнал» → `/media/smart_access/archive/journal-*.json`
  (видно в Медиа HA, переживает переустановку аддона), журнал очищается.
* Архивы скачиваются из панели; «Очистить журнал» — без архива.
* События также публикуются в MQTT (`smart_access/event`) и событием HA
  `smart_access_event` — фильтруйте по `action`.

## VLM (опционально)

OpenAI-совместимый endpoint: `base_url` (например `http://192.168.1.50:11434/v1`),
`api_key`, `model` (например `moondream`). Режимы: `gray_zone` (рекомендуется),
`verify_all`, `off`. При недоступности решение остаётся за локальными моделями.

## Журнал и события HA

* Сенсоры: `sensor.smart_access_status`, `sensor.smart_access_last_event`.
* События: `smart_access_event` (допуск/отказ/обучение), `smart_access_ack`.

## Диагностика

* Лог аддона: очередь событий, score матчей, ошибки MQTT/Frigate.
* Панель: счётчики сбоев камер моста, состояние моделей, статус Frigate —
  при «нет связи» панель показывает точную причину и что сделать.

## frigate_url и порты аддона Frigate

Официальная семантика портов Frigate (docs.frigate.video/configuration/advanced/system,
раздел «Listen on different ports»):

* **5000 — внутренний порт, БЕЗ аутентификации** (запросы считаются запросами
  администратора). Это главный порт для интеграции аддон↔аддон.
* **8971 — внешний порт, ТРЕБУЕТ аутентификации** (а у Frigate 0.16+ ещё и TLS
  с self-signed сертификатом). При выключенной аутентификации (`auth: enabled:
  false`) он отвечает HTTP 400 — это ожидаемо и НЕ значит, что Frigate сломан.
* Порты меняются в UI Frigate (Settings → System → Networking) или в YAML
  (`networking: listen: internal/external`); изменения вступают в силу после
  рестарта, порты должны быть разными.

Что это значит для Smart Access:

* Лучший адрес — **внутренний**: `http://<имя-аддона-Frigate>:5000`
  (например `http://ccab4aaf-frigate-fa:5000` — имя видно в журнале Smart
  Access). Имя аддона резолвится между аддонами, публикация портов на хост не
  нужна, аутентификация не мешает.
* Адреса вида `http://127.0.0.1:<порт>` работают только для портов,
  опубликованных на хосте, и подходят лишь для внешнего 8971 (да и то с
  оговорками по аутентификации).
* `/api/version` отвечает **plain text'ом** (`0.18.2`), а не JSON — Smart
  Access 1.1.10+ понимает оба формата (до 1.1.10 из-за строгой JSON-проверки
  живой Frigate 0.16+ выглядел как «нет связи»).
* Порядок авто-поиска (если настроенный `frigate_url` не отвечает):
  1) порты 5000 и 8971 того же хоста;
  2) скан внутренней сети аддонов (docker-мост hassio, стандартно
     172.30.32.0/23; env `SMART_ACCESS_BRIDGE_SUBNETS` для нестандартной);
  3) диагностика через Supervisor API: установлен/запущен ли аддон Frigate,
     его hostname для подсказки `http://<hostname>:5000`.
  Найденный адрес показывается в панели, используется автоматически (кэш
  10 мин, рескан при смене IP) и предлагается вписать в `frigate_url`.
* Если связи нет, панель дополнительно показывает **хвост журнала аддона
  Frigate** (1.1.10+, берётся через Supervisor API) — причина (например
  ошибка в config.yml) видна в конце.
* HTTP 401/403 от порта означают «Frigate найден, но порт требует
  аутентификацию» → используйте 5000 или отключите аутентификацию.
* MQTT-события (`frigate/events`) идут мимо frigate_url — через брокер.
  Если в опциях MQTT указан `localhost`/`127.0.0.1`/пусто, Smart Access 1.1.9+
  сам берёт у Supervisor адрес `127.0.0.1` и креды брокера. Статус
  подключения MQTT виден в панели рядом с хостом брокера. В сгенерированном
  конфиге Frigate `mqtt.host` подставляется как `core-mosquitto` — из
  мостового аддона Frigate `localhost` указывал бы на него самого.
* Частая ошибка — указать `8556`: это WebRTC (go2rtc), там нет API; 8554 —
  RTSP, 1984 — go2rtc API.
